# MVP de satélite web y procesamiento de voz centralizado

## Estado de esta decisión

Este documento describe una arquitectura experimental para reducir la carga de
las Raspberry Pi y mejorar el reconocimiento de la palabra de activación.

Por ahora **no se cambiará la pila gráfica existente**. El satélite continuará
usando Raspberry Pi OS Lite, Labwc y Cog/WPE en modo kiosco. La evaluación de
Cog directamente sobre DRM/KMS o Chromium sobre Cage queda aplazada hasta que
el MVP permita medir qué APIs web necesita realmente el cliente y cuánto cuesta
cada alternativa.

La implementación actual tampoco se elimina. El MVP debe convivir con ella
hasta demostrar en hardware real que la nueva arquitectura es más estable.

## Problema

Actualmente cada Raspberry ejecuta captura continua, detección local de wake
word, modelos Vosk/openWakeWord, segmentación del comando y TTS local. Las
Raspberry no están procesando ni reconociendo la wake word con suficiente
fiabilidad.

Mover el procesamiento al servidor puede permitir:

- Cargar una sola vez modelos de wake word y TTS más capaces.
- Aplicar la misma configuración a todos los satélites.
- Reducir CPU, RAM, temperatura y complejidad de instalación en las Raspberry.
- Conservar audio previo a una detección para diagnosticar falsos positivos y
  falsos negativos cuando el modo de diagnóstico esté habilitado.
- Actualizar modelos y umbrales sin desplegar software en cada satélite.

Centralizar el procesamiento no corregirá por sí solo una mala captura. Antes
de retirar la solución local hay que determinar cuánto del problema corresponde
al modelo o a la capacidad de la Raspberry y cuánto al micrófono, ganancia,
canal, ruido, eco o ubicación física.

## Arquitectura objetivo

```text
Raspberry / aplicación web
┌────────────────────────────────────────────┐
│ Display                                    │
│ getUserMedia + AudioWorklet                │
│ captura y resampleo liviano                │
│ reproducción de TTS                        │
│ eventos, estado y controles                │
└──────────────┬───────────────────▲─────────┘
               │ PCM mono 16 kHz   │ evento + URL/stream TTS
               │ continuo          │
               ▼                   │
Servidor
┌────────────────────────────────────────────┐
│ VoiceStreamSession por satelliteId         │
│ secuencia + timestamps + ring buffer       │
│       ↓                                    │
│ wake word central                          │
│       ↓                                    │
│ VAD / segmentación del comando             │
│       ↓                                    │
│ Whisper → agente → tools → Piper           │
└────────────────────────────────────────────┘

Raspberry
┌────────────────────────────────────────────┐
│ Sendspin daemon → parlante                 │
└────────────────▲───────────────────────────┘
                 │ música
          Music Assistant
```

### Responsabilidad de la Raspberry durante el MVP

- Mostrar la aplicación web.
- Obtener permiso y capturar el micrófono desde el navegador.
- Convertir el audio a mono PCM de 16 kHz con trabajo local mínimo.
- Enviar bloques continuamente al servidor.
- Mostrar niveles, conexión y estados de la conversación.
- Reproducir el TTS producido por el servidor.
- Mantener el daemon Sendspin actual para música.

La Raspberry no debe ejecutar wake word, Whisper ni Piper en el modo nuevo.

### Responsabilidad del servidor

- Autenticar e identificar cada satélite.
- Mantener una sesión de audio independiente por `satelliteId`.
- Validar secuencia, timestamp, formato y límites de cada stream.
- Mantener un ring buffer de varios segundos.
- Ejecutar wake word, VAD, segmentación y STT.
- Invocar el agente y sus tools existentes.
- Sintetizar TTS y entregarlo al satélite correcto.
- Publicar estados y métricas operativas.
- Recuperarse de desconexiones sin duplicar activaciones.

## Transporte del MVP

El primer prototipo usará **WebSocket binario con PCM mono de 16 kHz y 16
bits**. No se comenzará con WebRTC.

Motivos:

- El proyecto ya usa Node.js y `ws`.
- Wake word y Whisper terminan necesitando PCM.
- Es fácil inspeccionar, guardar y reproducir exactamente los bloques recibidos.
- Evita incorporar desde el comienzo SDP, ICE, STUN, TURN y decodificación
  Opus.
- El ancho de banda es aceptable dentro de la LAN.

PCM mono de 16 kHz y 16 bits utiliza aproximadamente 32 KB/s o 256 kbit/s por
satélite. El objetivo inicial es probar dos satélites en la misma red local.

Cada bloque debe incluir o estar asociado a:

- `satelliteId` y una identidad de sesión.
- Número de secuencia monotónico.
- Timestamp de captura monotónico.
- Formato y frecuencia de muestreo negociados al abrir la sesión.
- Estado de captura y motivo de cierre.

Los bloques deberían representar inicialmente entre 20 y 40 ms. El cliente
debe observar `bufferedAmount` y aplicar una política explícita de backpressure.
Si la cola crece, debe descartar audio antiguo y reconectar o reiniciar la
sesión; nunca debe reproducir en el servidor una escucha retrasada varios
segundos.

WebRTC/Opus se evaluará después sólo si las mediciones muestran pérdidas,
jitter, ancho de banda o necesidad de acceso remoto que WebSocket PCM no pueda
resolver adecuadamente.

## Entrega de TTS

Para el MVP, Piper correrá en el servidor. Al terminar la síntesis, el servidor
publicará un evento dirigido al `satelliteId` que contenga una URL temporal y
el tipo MIME. La página reproducirá el audio con un elemento `<audio>`.

Esta solución es más simple que implementar audio bidireccional en tiempo real.
La transmisión progresiva del TTS podrá evaluarse después si la latencia de una
respuesta completa resulta perceptible.

Durante el TTS se pausará o ignorará temporalmente la captura, conservando el
comportamiento actual. Barge-in y AEC reales quedan fuera del MVP.

## Música y Music Assistant

El daemon Sendspin actual se conserva inicialmente. La migración de voz no debe
acoplarse a Music Assistant ni alterar `MusicGateway`.

Sendspin y su reproductor web son candidatos para una etapa posterior, pero no
se utilizará el rol `source` de Sendspin como transporte de voz en el MVP:

- Music Assistant sería el receptor del stream, no el backend del asistente.
- Sería necesario extraer o redirigir el audio desde Music Assistant.
- El protocolo todavía está evolucionando.
- Mezclaría el ciclo de vida de voz con el de reproducción musical.

Una vez estable la voz centralizada se podrá comparar por separado:

1. Mantener el daemon Sendspin nativo.
2. Incorporar un cliente Sendspin en la página del satélite.

## Pila gráfica

La configuración actual ya es liviana: Raspberry Pi OS Lite, Labwc y Cog/WPE,
sin un escritorio completo. El MVP debe ejecutarse primero sobre esta pila para
no cambiar simultáneamente la arquitectura de voz y el entorno gráfico.

Después del MVP se evaluarán dos opciones:

### Cog/WPE directamente sobre DRM/KMS

Sería la alternativa de menor peso porque elimina Labwc. Requiere validar en el
paquete real de Raspberry Pi OS:

- Backend DRM disponible.
- Pantalla táctil y rotación.
- `getUserMedia`.
- `AudioWorklet`.
- WebSocket binario continuo.
- Reproducción de audio y permisos.

### Chromium sobre Cage

Cage es un compositor Wayland de una sola aplicación que puede ejecutarse desde
TTY sobre KMS/DRM. Chromium ofrecería mayor compatibilidad con APIs de audio,
permisos, WebRTC y un futuro cliente Sendspin web, a cambio de mayor consumo que
Cog.

Xorg sin escritorio también es posible, pero no es la opción preferida. Un
Chromium estándar tampoco debe suponerse capaz de ejecutarse directamente sobre
DRM/KMS: el backend Ozone DRM no suele estar disponible en los paquetes Linux
normales de la misma manera que en ChromeOS.

La decisión futura se tomará con mediciones, no sólo por cantidad de procesos.

## Seguridad y privacidad

La captura continua requiere:

- Identidad persistente por satélite.
- Emparejamiento o credencial de dispositivo.
- Autorización del servidor antes de aceptar audio.
- Límite de sesiones, tamaño de bloque, frecuencia y ancho de banda.
- Indicador visible de que el micrófono está activo.
- Control claro para silenciarlo.
- No persistir audio ambiental de forma predeterminada.
- Modo diagnóstico explícito, limitado y con retención definida.
- TLS si el tráfico sale de una LAN considerada confiable.

`getUserMedia` exige un contexto seguro. El display local servido desde
`http://localhost:8080` cumple esa condición especial del navegador. Si en el
futuro la página se sirve desde el backend mediante una IP de red, deberá usar
HTTPS.

## Estrategia dentro del repositorio

No se creará otro repositorio y no se reescribirá el proyecto desde cero. Deben
reutilizarse el display, contratos, descubrimiento, identidad, agente, tools,
Whisper, administración de modelos y MusicGateway existentes.

La implementación se realizará en una rama nueva, sugerida:

```text
experimental-central-voice
```

Antes de crearla hay que preservar explícitamente los cambios actuales de la
rama `experimental-wake-word-detection` mediante un commit de checkpoint o el
mecanismo acordado para no mezclar trabajos incompletos.

Estructura tentativa:

```text
apps/
    server/
        src/voice-stream/
    display/
    web-satellite/
    satellite/
```

`apps/satellite` se conserva durante el experimento. El servidor debe admitir
temporalmente ambos modos:

- Modo existente: wake word local y `POST /stt/transcribe`.
- Modo nuevo: stream continuo y wake word central.

Una Raspberry puede ejecutar el modo nuevo y la otra actuar como control. El
código local de Vosk/openWakeWord/Piper sólo se eliminará después de una prueba
prolongada satisfactoria.

## Alcance del primer vertical slice

El primer resultado demostrable debe hacer únicamente lo siguiente:

1. La página solicita permiso de micrófono.
2. `AudioWorklet` obtiene audio sin bloquear la UI.
3. El cliente genera PCM mono de 16 kHz.
4. El cliente abre una sesión autenticada y envía bloques binarios.
5. El servidor mantiene secuencia, métricas y ring buffer por satélite.
6. El servidor detecta una wake word.
7. El servidor delimita y transcribe un comando.
8. El agente genera una respuesta sin cambiar sus tools actuales.
9. Piper sintetiza en el servidor.
10. La página recibe el evento y reproduce el TTS.
11. Una pérdida de conexión termina la sesión y permite reconectar sin generar
    una activación duplicada.

No forman parte de este vertical slice:

- WebRTC.
- Opus.
- Barge-in.
- AEC por software.
- Audio fuera de la LAN.
- Sustitución del daemon Sendspin.
- Cambio de Labwc/Cog.
- Eliminación del satélite actual.

## Pruebas previas y plan de desarrollo

### Fase 0: línea base

En ambas Raspberry medir:

- CPU y RSS de Cog, Labwc, Node, FFmpeg, Vosk/openWakeWord, Piper y Sendspin.
- Temperatura y throttling.
- Canal elegido, RMS, clipping y ruido.
- Wake words detectadas y omitidas.
- Falsos positivos con silencio, televisión, TTS y música.

Guardar un conjunto controlado de WAVs y ejecutar exactamente esos archivos en
el servidor con el modelo y umbral actuales. Si los mismos WAVs fallan en un
servidor con recursos suficientes, el problema no es sólo la Raspberry.

### Fase 1: spike de transporte

- Capturar desde la página.
- Enviar PCM al servidor sin ejecutar todavía el agente.
- Reconstruir WAVs de diagnóstico en pruebas controladas.
- Medir huecos, secuencia, latencia, cola y reconexión.
- Mantenerlo varias horas en cada Raspberry.

### Fase 2: wake word central

- Agregar detector y ring buffer por sesión.
- Probar uno y dos streams simultáneos.
- Medir score, falsos positivos por hora y detecciones omitidas.
- Probar con música reproduciéndose desde Sendspin.
- Cortar y restaurar Wi-Fi durante la escucha.

### Fase 3: conversación completa

- Integrar VAD, Whisper, agente y tools.
- Ejecutar Piper en el servidor.
- Entregar y reproducir el TTS.
- Pausar o ignorar captura durante la respuesta.
- Mantener memoria conversacional por `satelliteId`.

### Fase 4: prueba prolongada

Ejecutar una Raspberry en modo nuevo y la otra en modo actual durante varios
días. Comparar fiabilidad, uso de recursos, temperatura y experiencia de uso.

### Fase 5: decisiones posteriores

Con los resultados se decidirá por separado:

- WebSocket PCM frente a WebRTC/Opus.
- Cog/Labwc frente a Cog/DRM o Chromium/Cage.
- Sendspin daemon frente a Sendspin web.
- Retiro o conservación del modo de voz local como fallback.

## Métricas y criterios de aceptación

El MVP debe registrar como mínimo:

- CPU y RAM en Raspberry y servidor.
- Latencia de captura a recepción.
- Latencia desde wake word a estado de escucha.
- Latencia desde fin del comando a transcripción.
- Latencia total hasta el comienzo del TTS.
- Bloques perdidos, fuera de orden o descartados.
- Reconexiones y duración de cada interrupción.
- Falsos positivos por hora.
- Wake words omitidas sobre un conjunto de pruebas repetible.
- Éxito de reproducción TTS.

Antes de retirar la implementación local deben cumplirse estas condiciones:

- Funcionamiento estable con al menos dos satélites simultáneos.
- Ausencia de retraso acumulativo del stream.
- Recuperación automática después de perder la red o reiniciar el servidor.
- Mejora verificable del reconocimiento respecto del modo local.
- Reducción verificable de CPU/RAM/temperatura en las Raspberry.
- TTS dirigido siempre al satélite correcto.
- Música mediante Sendspin sin regresiones.
- Funcionamiento prolongado sin intervención manual.

Los valores numéricos definitivos de latencia y tasa de error se fijarán después
de obtener la línea base de las Raspberry actuales.
